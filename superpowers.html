01 / OVERVIEW

先理解這套工具

Superpowers 是 Jesse Vincent（obra）與團隊維護的 coding agent 開發方法。本文以 官方 README 的 Skills Library 為範圍，列出 15 個 skills；分類沿用官方。

讀這篇時，注意兩件事

這套工具會依情境檢查並啟動相關 skills；不用把所有名稱都當成需要逐一輸入的命令。下面的箭頭是流程示意，實際呼叫方式依 agent 而異。

brainstorming、plan、review 等也可能是階段名稱；規格審查與計畫審查不代表另有同名 skill。本文是在整理工具，沒有替此網站安裝或執行 Superpowers。

官方基本流程

brainstorming→using-git-worktrees→writing-plans→執行計畫→審查與收尾

實作時配合 TDD；執行可選逐任務子代理或同一 session。官方流程原文 ↗

這是完整功能開發的導覽，不是要求所有小改動都產生長篇文件。請以安裝版本的 skill 原文判斷所需步驟。

02 / WORKFLOWS

別人怎麼把它用進工作裡

以下是實際使用者的經驗摘要。適用情境與操作提示為本筆記整理，成效不代表所有任務都能複製。

Aaron Sumner · 初學者與學習

先與 agent 並肩做，再逐步增加委派

Aaron 會先提供背景，透過 brainstorming 釐清需求，較大工作再寫成 Markdown 計畫。他建議新手或不熟悉的工作先採逐步協作，在過程中停下來審查與回饋，甚至讓計畫安排教學時刻。

brainstorming→可閱讀的計畫→分段實作＋人工回饋

適用：學習新 codebase、第一次使用 agent 開發。熟悉後再交給子代理；他也提醒較大工作會消耗更多 tokens。

來源：Left of the Dev · 2026-02-19 ↗
Bob Ulrich · 複雜功能

在實作前，先審查規格與計畫

Bob 以照片隨機排序功能說明：先透過訪談釐清漸進載入、deep links 與 lightbox 行為，寫出規格並審查缺口；再把規格轉成小任務計畫，檢查需求是否被覆蓋，最後實作與審查。

brainstorm→spec＋review→plan＋review→implement＋review

適用：牽涉既有系統、多種邊界情境的功能。文章描述的多代理平行實作屬他的案例，不應推論每一份計畫都適合平行修改。

來源：BDIGITAL · 2026-04-02 ↗
Gautam Khorana · 內容與研究

把釐清與計畫方法延伸到非程式工作

Gautam 會先用 brainstorming 確認文章的讀者與角度，再用 writing-plans 安排系列文章、內部連結與研究任務。彼此獨立的研究分給不同 agents，最後集中整理。

讀者與目標→內容計畫→獨立研究→整合與品質檢查

適用：多篇內容、整理學習資料。這是使用者延伸玩法，TDD 與 code-review 的原始內容仍以軟體開發為主；不能直接把測試通過當成文章正確。

來源：Gautam Khorana · 2026-05-06，更新 2026-07-04 ↗
Reddit 使用者 · 縮小回饋週期

任務太大時，先切 MVP，再檢查結果

在 review workflow 討論中，有使用者偏好 pair coding：把大功能先切成 MVP 或骨架，縮短每次等待與審查範圍。其他使用者則先拆 user story，再把明確任務委派出去，稍後統一檢查。

小範圍計畫→MVP／骨架→人工確認→下一輪

適用：不想長時間失去進度可見性的工作。留言也有人停用 worktree 或自動審查；這是個人調整，不是官方預設或本筆記的必要建議。

來源：r/ClaudeAI · Review workflow 討論 ↗
本筆記建議的起點

選一個邊界清楚的小功能，先討論需求與驗收條件。閱讀設計與計畫後，逐段確認實作；等你能判斷結果，再擴大委派範圍。

04 / GET STARTED

把筆記帶進工作裡

  1. 依使用的 agent 安裝

    不同 agent 的安裝方式不同，請查閱 官方安裝說明。安裝完成後，確認新 session 能辨識相關 skills。

  2. 給 agent 背景與明確產物

    以下是本筆記自寫的起始範例；先用需求討論建立理解。

    請用 Superpowers 的 brainstorming，幫我規劃筆記網站的標籤功能。
網站目前是純靜態 HTML，主題會持續增加。
請先釐清標籤用途、篩選行為與驗收條件，讓我確認設計。
若需要多步驟實作，再整理可逐項檢查的計畫。
  3. 把驗收方式放進計畫

    例如：新增主題能套用既有標籤、手機能操作、沒有結果時有提示。完成時實際操作這些情境，再決定後續收尾。

  4. 流程本身異常時，也要留下證據

    若 skill 沒觸發、重複工作或偏離計畫，可使用 diagnosing-superpowers 檢查 session；這與調查應用程式 bug 的 systematic-debugging 是不同問題。

與上一篇一起讀

本筆記的比較：Matt Pocock skills 的清單明確區分使用者啟動與模型可選用；Superpowers 更強調自動檢查相關 skills 與串接工作流程。第一次練習可先選一套作為主要流程，方便理解每一步由誰負責。
